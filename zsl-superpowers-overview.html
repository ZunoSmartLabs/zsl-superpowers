1. Orientation

ZSL Superpowers is a 23-skill Claude Code plugin. The point is not any one skill — it's that most skills compose into a single engineering loop. The plugin is opinionated about workflow, not style. Learn the loop and every skill finds its place.

Before the loop, one structural fact. The repo is three concentric layers — you only ever edit the middle one:

  • Knowledge is the 23 SKILL.md files — Markdown with frontmatter that tells the harness when to fire. This is the product.
  • Runtime is Claude Code itself. Skills are not harness-agnostic: they lean on Agent, Monitor, SendMessage, worktrees, slash commands.
  • Distribution is the packaging. plugin.json lists the 23 skills; the marketplace serves them; a version bump auto-releases.

That raises: if the skills are the product and they compose into a loop — what is the loop?

4. AFK vs HITL — the dependency contract new in 0.6

When /to-issues breaks a plan into vertical slices, every slice gets a title of the form [AFK|HITL] <wave><letter> — description. That prefix is the dependency contract the build phase consumes:

  • [AFK] — an agent can run it unattended. /tdd-parallel fans these out into worktrees in parallel.
  • [HITL] — a manual action a coding agent physically cannot perform: a third-party console click, a credential rotation, external sign-off, a hand-run production migration.
  • <wave> — serialisation level (wave 1 lands before wave 2).
  • <letter> — parallelism within a wave (same wave = disjoint, runnable together).
The v0.6 sharpening. Before 0.6, [HITL] was defined loosely as "needs human interaction, such as an architectural decision or a design review." That conflated two unlike things. A decision is not a HITL slice — it should be resolved upstream in /grill-with-docs and recorded as an ADR before issues are cut, so slices fall out maximally AFK. A [HITL] slice that's really a decision in disguise is a process leak, not a unit of work.

So the build phase routes a slice by what kind of thing it is:

/tdd-parallel filters [HITL] out of the fanout — unattended sub-agents can't stop and wait for a human on every slice. The new /human-itl skill is the serial, human-present counterpart: it walks you through each manual-action slice, records what you did as an audit-trail comment, marks it done so the [AFK] slices that were Blocked by it unblock, then stops with the hint to re-run /tdd-parallel — it never writes code (that's /tdd) and never chains the fanout for you.

Why this matters as a teaching point. The old advice — "run skipped HITL slices with /tdd" — was incoherent: you don't red-green-refactor a console click or a decision. v0.6 makes the three cases distinct and gives each its own home: manual action → /human-itl, decision → /grill-with-docs + ADR (upstream), code → /tdd / /tdd-parallel. The goal of the loop is that by the time a fanout kicks off, every decision is already settled and the only [HITL] slices left are genuine manual actions.

Every issue carries one category role (bug | enhancement) and one state role (the boxes above). The whole triage skill is just an interactive walk of this graph. A PRD becomes a tracking container; its sliced children move needs_triage → ready_agent and the build phase takes over.

6. Two orthogonal config axes

/setup-zsl-superpowers writes docs/agents/*.md once per repo. Two of those files independently change build/ship behavior. They are orthogonal — every combination is valid.

Axis 1 — ship style (docs/agents/ship-style.md): what gets pushed

Ship styleWhat /tdd does at step 5
PR-styleCommits via /commit, pushes the branch, opens a PR. Merge to main happens externally on approval.
direct-pushCommits via /commit, pushes the branch. You merge by hand. (Blocks /tdd-parallel, which needs PR-style consolidation.)

Axis 2 — issue tracker (docs/agents/issue-tracker.md): how a sub-task closes

TrackerHow the sub-task closes
GitHub / GitLabCloses #<n> — in the PR body (PR-style) or commit body (direct-push). Parent auto-closes when its last child closes.
local-markdownNo Closes #N. Flip the issue file's Status: to shipped and git mv it into issues/done/, in the same commit as the slice's code.
Orthogonal. PR-style + local-markdown pushes a PR and does the git mv; direct-push + local-markdown commits the git mv straight to the branch. "What gets pushed" and "how it closes" are read from different files and never interact.

7. The build phase in depth

/tdd and /tdd-parallel diverge most in branching. Standalone /tdd works on whatever branch you hand it. /tdd-parallel stages a multi-branch worktree dance and consolidates it into one PR.

7a. Standalone /tdd

/tdd doesn't create branches — it inherits the caller's branch (you usually make it with /git-branch first). It runs red-green-refactor, then ships at step 5 by default (suppressed only by --no-ship) — but never silently: it asks for confirmation before pushing or opening a PR.

7b. /tdd-parallel orchestration

The orchestrator manages three branch layers. The key trick: the parent PRD branch doubles as the integration branch. Slices never merge to main directly — they merge to the PRD branch, which is pushed exactly once at the end as a single integration PR — but only after the step-4a coverage gate clears (§8). [HITL] slices are filtered out (see §4); clear them with /human-itl and re-run.

Why worktrees + per-slice branches? So commits don't interleave on a shared branch and the orchestrator owns the merge order. Why one PR? Every push triggers CI; N slices × M workflows is wasted minutes. One consolidated push = one CI run. Trade-off: no per-slice review granularity — acceptable because /to-issues's wave model already asserts same-wave slices are disjoint. Why --no-ff? So git log --first-parent reads the wave shape later. Inheritance: wave 2 worktrees branch from the PRD tip, which already contains wave 1's merges — which is exactly why same-wave slices must be disjoint.

7c. "Can't I just run /tdd twice on the PRD branch?"

Common question. Short answer: only one clean path exists. Running two /tdds on a shared branch breaks PR creation — the first ship opens the PR, the second gh pr create refuses ("already exists for branch") and only the first slice's Closes #N lands. The fix is the decision tree below.

Pattern A is the native rhythm: each slice is a tracer bullet that earns its own PR; if slice 2 goes sideways, slice 1 is already in main. Want one bundled PR? Just use /tdd-parallel — even for two slices, with --max 1 for strictly serial execution. Pattern C (manual --no-ship twice then push) is only for direct-push repos where /tdd-parallel is off-limits.

That raises: the fanout opens one PR the moment every slice merges — but "all slices merged" is not "the PRD was delivered." How does the loop tell the difference?

8. The coverage gate — did we build what the PRD promised? new in 0.7

Until 0.7 the only post-build completeness signal was structural: the tracker auto-closes the PRD when its last child closes. But "every slice shipped" is not "every user story is covered" — they diverge exactly when slicing drops or misframes a story. /verify-coverage closes that gap, and /tdd-parallel step 4a enforces it.

It takes the PRD's ## User Stories as an acceptance oracle (never as implementation context — /tdd deliberately never sees it) and proves each story against the implemented code via tests, not prose. The oracle, weakest to strongest:

  1. Prose vs prose — LLM judges. Rejected.
  2. Prose vs code search — confirms code looks related, not that it works. Demoted to a hint.
  3. Tier A — prose vs an existing passing test that exercises the story's observable behaviour.
  4. Tier B — prose vs a generated test: write one, prove it non-vacuous by mutation (perturb the code, confirm RED, revert), then run it. GREEN = covered; RED = a real gap with a failing test as the receipt.

Stories no assertion can capture (visual/UX, real external systems) route to a HITL lane for human attestation — the same AFK/HITL split from §4. Genuine gaps are quarantined as skipped tests and auto-filed as needs-triage sub-issues of the PRD, so they re-enter the loop through /triage → /tdd-parallel.

Execution gate, not outcome gate. The gate enforces that the check ran against the integrated tip — never that the matrix came back clean. Open gaps still pass (they ride a later fanout); only skipping the check is blocked. The receipt records mode:full + the verified sha; a --no-generate partial run or a receipt for an older sha is rejected. The matrix outcome itself stays a review surface that ends in a human decision — the two notions never collapse into "block the PR until coverage is clean."

Adding or removing a skill is not one edit. It's five, plus a release dance.
